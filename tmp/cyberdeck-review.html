Behavior bugs

Save/load silently drops half the state — guard checks for a field that doesn't exist
src/CyberDeck/utils/SaveLoad.ts:163-167 (isComponentCounts)

The components validator requires an "ICE" field and obj.ICE to be a number. The actual data has ICEBreakers. Every load throws "Invalid cyberdeck savestring value: components", the catch swallows it, and everything below that check in loadCyberdeckSaveData — componentStats, netrunningSeedUsages, netrunningCorruptedSeedUsages, craftingPowerSupplySeedUsages, craftingProcessingModSeedUsages, craftingUplinkSeedUsages — never loads. Testers will see components reset, componentStats blank, and seed-driven RNG re-randomize on every refresh.

Rename "ICE" to "ICEBreakers" and obj.ICE to obj.ICEBreakers (twice each). While you're there, add a cores check — it's in the type but not the guard.

Cyberdeck server RAM and core upgrades vanish on refresh
src/CyberDeck/utils/SaveLoad.ts:6-27 (CyberdeckSaveData)

serverRamUpgrades and serverCoreUpgrades are on CyberdeckState but never included in the save data type, written by getCyberdeckSaveData, or loaded by loadCyberdeckSaveData. After a refresh, both reset to 0 and addCyberdeckServer rebuilds the server with maxRam = 4, cpuCores = 0. All the components and money the player spent on upgrades are gone.

Add both fields to CyberdeckSaveData, write them in getCyberdeckSaveData, validate + assign them in loadCyberdeckSaveData. addCyberdeckServer already uses the state values, so no further wiring needed.

Custom cyberdeck build takes 200 real-time hours (unitRate is 1)
src/Work/CreateCyberdeckWork.tsx:20

this.unitRate = 1 and unitNeeded = MillisecondsPerHour = 3,600,000. With one cycle per 200ms tick, unitCompleted grows by ~1 per tick — 5 per real-time second — so the build finishes in 3.6M ticks ≈ 200 hours. Compare CreateProgramWork which uses unitRate = MilliPerCycle * skillMult ≈ 200+. The constant name MillisecondsPerHour implies the intent was ~1 hour.

Set this.unitRate = CONSTANTS.MilliPerCycle. That gets you ~1000 units/sec and the build finishes in ~1 hour of focused work, matching the constant name.

Two crafting seed counters aren't reset on bitnode prestige
src/CyberDeck/utils/prestigeCyberdeck.ts:22

The bitnode reset resets netrunningSeedUsages, craftingPowerSupplySeedUsages, and netrunningCorruptedSeedUsages, but skips craftingProcessingModSeedUsages and craftingUplinkSeedUsages. Second-bitnode crafting will roll from stale counter positions, so the RNG isn't deterministic across a fresh bitnode start.

Add both fields to the bitnode reset block: CyberdeckState.craftingProcessingModSeedUsages = 0; and CyberdeckState.craftingUplinkSeedUsages = 0;

Netrun succeeds with 0 free storage slots, overflowing storage by 3
src/CyberDeck/models/netrun.ts:51 and src/CyberDeck/cyberdeckApi.ts:174

The check is modStorageSize >= storedModules.length (in canNetrun) or modStorageSize < storedModules.length (in the API guard). If storage is exactly full — say 8/8 — both conditions pass and the netrun proceeds. getNetrunningRewards unshifts 3 mods, leaving storage at 11/8. Same for corrupted netrun.

Require 3 free slots: storedModules.length + 3 <= modStorageSize. Or expose the "netrun returns 3 mods" as a shared constant and use it in both checks.

Corrupted mods' extra debuff never applies (??= can't fire)
src/CyberDeck/models/createCorruptedModule.ts:34 and :42

module.stats.playerMults ??= mergeBuffs(getDebuff(8, rng), module.stats?.playerMults ?? {}); — but createProcessingModule and createUplink always set stats.playerMults to at least {}, so it's never nullish. The ??= never fires. The intended "add a nastier debuff on top of the base one" is a silent no-op for these corrupted branches.

Change ??= to =: module.stats.playerMults = mergeBuffs(getDebuff(8, rng), module.stats?.playerMults ?? {});

In-flight cortexShare() thread count doesn't reset on bitnode prestige
src/CyberDeck/utils/prestigeCyberdeck.ts (bitnode block)

CyberdeckState.cortexSharedThreads is incremented at the start of a scripted cortexShare() and decremented in its .finally(). On bitnode prestige scripts are killed mid-flight — the finally may not run — leaving a stale non-zero count. The next tick's gainCyberdeckComponents() in the new bitnode reads that stale value and hands out phantom neurodes from the cortex source.

In the bitnode reset block, add CyberdeckState.cortexSharedThreads = 0;

Fresh cyberdeck server has cpuCores = 0
src/CyberDeck/models/cyberdeckServer.ts:33

server.cpuCores = CyberdeckState.serverCoreUpgrades, which is 0 until the player buys an upgrade. Every real server has ≥1 core; grow/weaken and similar formulas assume it. A cyberdeck server with 0 cores will misbehave for scripts running on it.

server.cpuCores = 1 + CyberdeckState.serverCoreUpgrades; — matches how RAM is 4 + serverRamUpgrades. Update upgradeCyberdeckServerCores's server assignment the same way.

Netrun trace risk shows increasing % after cooldown expires (goes past 100%)
src/CyberDeck/models/netrun.ts:45

((netrunningTraceDecayMs - timeSinceLastRun) / netrunningTraceDecayMs) ** 2. Once timeSinceLastRun > decay, the numerator goes negative; squaring makes it positive. API gaps

★ No server.canUpgradeRam() — cost getter returns Infinity when maxed, poisoning downstream checks
src/CyberDeck/cyberdeckApi.ts:226 (server.getRamUpgradeCost)

When RAM is maxed, getCyberdeckServerRamUpgradeCost returns {componentCost: {ROM: Infinity, neurodes: Infinity, chips: Infinity, ...}, moneyCost: Infinity}. The API spreads that into {ROM: Infinity, chips: Infinity, ..., money: Infinity}. Scripter code like if (cost.money < player.money) upgrade() reads "money we need is Infinity, so we can't afford it" — no way to distinguish that from "expensive but not maxed".

Add server.canUpgradeRam(): boolean (and canUpgradeCores(): boolean for symmetry, even though cores has no cap yet). Alternatively return null from the cost getter when maxed, but that's a breaking type change.

No API to observe netrun trace cooldown / decay progress
src/CyberDeck/cyberdeckApi.ts (Cyberdeck namespace)

Scripters can call getNetrunningCost() to see the current ICE cost, but that's a lagging indicator. They can't tell how close the cost is to fully-decayed, or how long until the next cheap netrun. To auto-schedule netruns optimally they'd need to poll getNetrunningCost() in a busy loop, which is wasteful.

Expose either getNetrunningTraceFraction(): number (0..1, matches the UI's "hostile trace risk"), or getMillisSinceLastNetrun(): number. Same for corrupted.

getLevels().modStorageSize is a capacity, not a level — surprising in a "levels" record
src/CyberDeck/cyberdeckApi.ts:216 (stats.getLevels)

The getLevels() return has netrunningLevel, craftingLevel, netrunningCooldownLevel, and then modStorageSize. Only one of these isn't a level in the sense of "consumed from skill chips over time" — modStorageSize is a slot count. Scripters comparing "levels" to bound their farm will trip over this.

Either rename the return field (breaking, but pre-launch is the right time), or add a dedicated getStorageCapacity(): number.

No API to read the current rack capacity
src/CyberDeck/cyberdeckApi.ts (Cyberdeck namespace)

Rack capacity is baseRackSize + extraRackSlots from charged Rack Extensions. Scripters have no way to read it — they'd have to sum getInstalledMods().filter(charged).reduce((s,m) => s + (m.stats?.extraRackSlots ?? 0), 0) plus a hardcoded base. Fragile and duplicative.

Add getRackCapacity(): number returning getCurrentRackSize(). Bonus: getMaxInstalledRackExtensions(): number so scripters know when Rack Extension installs will fail.

recycleMod throws for missing mod but returns {success: false, ...} for favorited mod
src/CyberDeck/cyberdeckApi.ts:416-429

Two error paths with two shapes: throw new Error('not found') for a bad ID, and {success: false, chips: 0, ...} for a favorited mod. Scripters have to wrap in try/catch AND check result.success. Would be nicer to pick one convention.

Return {success: false, ...} for both (log the reason via logger(ctx)), OR throw for both. Either is fine; consistency is what matters.

favoriteMod throws if called on the IO panel — with the same message shape as "not found"
src/CyberDeck/cyberdeckApi.ts:78-83 → getModOrThrow:37-52

Calling favoriteMod(ns.cyberdeck.getCyberdeckIOPanel().id) throws "Cannot modify the IO Panel". The scripter's action was favorite, not modify — the message is misleading. And getModOrThrow's "not found" throw and this IO-panel throw are both bare Errors, so try/catch can't distinguish them.

Either allow favoriting the IO panel (harmless), or throw a specific message: "IO Panel cannot be favorited". Consider distinct error subtypes.

No way for a script to observe hasDiscoveredGlitch state
src/CyberDeck/cyberdeckApi.ts (legacy namespace)

The legacy.getCost and legacy.delve APIs both silently print a corrupted hint if the glitch isn't discovered yet, and return Infinity / {success:false}. A script that wants to gate work on "player has discovered the glitch" has no direct predicate to check.

Add legacy.hasDiscoveredGlitch(): boolean. Or fold it into a hasCyberdeck()-shaped predicate.

Footguns for scripters

Fractional modStorageSize from skill chips is silently wasted
src/CyberDeck/models/moduleMutation.ts:266; comparisons in netrun.ts:52, cyberdeckApi.ts:174, NetrunningPortal.tsx:99

Skill chips add fractional slot counts (e.g., +0.32). So modStorageSize becomes 8.32. All the "is storage full" checks use < storedModules.length: 8.32 < 9 is true, so the 9th slot never materializes. The player pays for a fractional bonus that never turns into an actual slot. The UI's Math.floor(modStorageSize) displays honestly, but the number just slowly grows toward a threshold that never registers.

Either round skill chip storage buffs up on consumption (Math.ceil(stats.mod_storage) before adding), or floor modStorageSize in all the guard comparisons. Preferably: Math.floor(modStorageSize) < storedModules.length + 3.

getID can pick a 32-value ID space; collision retry can spin
src/CyberDeck/utils/statRng.ts:228-238

Bases are [2, 8, 12, 16] and IDs are Math.floor(random * base**5).toString(base). For base=2, that's 2**5 = 32 possible values. A player with many stored mods will hit collisions frequently, and the do…while retries until it lucks into a free one — potentially many iterations, and only re-rolling the numeric part means it can loop forever if all 32 base-2 IDs are taken and the rng happens to keep picking base=2.

Drop the small bases or bump the exponent so the smallest space is at least ~4x the max mod count. A cheap fix: const baseOptions = [8, 12, 16];

RAM upgrade button is enabled when the player can't afford it — silent no-op on click
src/CyberDeck/ui/CraftingPage.tsx:91

Only disabled on !canUpgradeCyberdeckServerRam() (the cap check). Not on affordability. Player clicks, upgradeCyberdeckServerRam returns false silently, nothing changes, no toast. Same for the cores upgrade button (which also lacks a cap and has NO disable state at all).

Disable on !canAffordCyberdeckServerRamUpgrade() too, OR fire a SnackbarEvent on failure. Apply the same to the cores button.

Cores upgrade has no cap — player can spend components/money forever with diminishing benefit
src/CyberDeck/models/cyberdeckServer.ts:91-127

No getCyberdeckServerCoreUpgradeCap exists. upgradeCyberdeckServerCores succeeds indefinitely. Player can grind to cpuCores = 100+, at which point grow/weaken formulas produce weird values. No UI hint that cores stop being useful past some ceiling.

Either add a cap (parallel to RAM's 28) and update the UI "Maxed" state, or document that cores are uncapped. If uncapped is intentional, at least the cost curve should telegraph "diminishing returns".

addConnection(a, b, socket) requires the same socketIndex on BOTH mods — undocumented
src/CyberDeck/models/moduleMutation.ts:78-129 (createConnection) and NetscriptDefinitions.d.ts:4603-4620

The impl builds {modId1, socketIndex} and {modId2, socketIndex} — same index on both ends. If mod A has socket 3 but mod B doesn't, the connection fails with "Socket colors do not match." The .d.ts hints at "socket colors" but doesn't spell out the invariant that the same socketIndex slot must exist on both mods. Scripters will spend time trying socket permutations before figuring it out.

Add a line to the JSDoc: "Both mods must have a socket at socketIndex. Use mod.sockets[socketIndex] to check."

installMod costs 1 second each — batch installs are painfully slow
src/CyberDeck/cyberdeckApi.ts:96

Every installMod awaits helpers.netscriptDelay(ctx, 1000). A script that installs 5 mods takes 5s of wall time even without any real work in between. Doesn't scale for auto-swapping loadouts.

Either shorten the delay (200-500ms), or add an installMods(ids: string[]) batch method with a single delay, or at least document the delay so scripters aren't surprised.
