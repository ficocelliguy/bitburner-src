Behavior bugs

★ Normal netrun crashes on the 3rd move — groups[-1] is undefined
src/CyberDeck/models/netrunningMinigame.ts:253 (spreadOfflineNodes)

move() calls spreadOfflineNodes() on every step. That function increments NetrunningState.steps and, when steps % 3 === 0, does NetrunningState.groups[-1].slice(0). groups[-1] is only ever seeded in initNetrunGrid when corrupted === true. For a normal netrun, groups[-1] is undefined — the third move throws TypeError: Cannot read properties of undefined (reading 'slice') and the run wedges. Testers will hit this immediately.

Early-return when there are no offline nodes: if (!NetrunningState.groups[-1]?.length) return; at the top of spreadOfflineNodes, or seed an empty groups[-1] = [] in initNetrunGrid for both branches.

★ payComponentCost never deducts cores — power supply / processing mod / uplink craft cores-free
src/CyberDeck/models/createModule.ts:258-263

payComponentCost subtracts chips, rom, neurodes, iceBreakers — but not cores. The affordability check (canAffordComponentCost) DOES require cores, so the crafting cost tooltip and gate both mention the cost, but nothing is actually spent. Every craft that lists cores: 1 (power supply, processing, uplink) is effectively cores-free.

Add CyberdeckState.components.cores -= (cost.cores ?? 0) * count; to payComponentCost.

Netrun still succeeds with 0 free storage slots, overflowing storage by 1-4
src/CyberDeck/models/netrunRewards.ts:57-60 (canNetrun) and cyberdeckApi.ts:240

The check is modStorageSize >= storedModules.length. If storage is exactly full — say 8/8 — 8 >= 8 passes and the netrun runs. getNetrunningRewards unshifts 1-4 mods based on score, so a full-storage player ends the run at 9/8 to 12/8. Same off-by-N as before; only the count of added mods changed.

Reserve at least one slot: storedModules.length + 1 <= modStorageSize. Ideally reserve the worst case (4) since score is unknown at gate time, or expose a getMaxNetrunRewardCount() constant and gate on that.

Tutorial progress mid-checklist doesn't survive a refresh
src/CyberDeck/utils/SaveLoad.ts:6-30 (CyberdeckSaveData); CyberdeckState.tutorialSteps

CyberdeckState.tutorialSteps tracks the six per-item flags shown in TutorialChecklist. Save data has hasCompletedTutorial but not the individual step flags. A tester who does 5 of the 6 steps and reloads will see 0/6 again — all their check marks reset.

Add tutorialSteps to CyberdeckSaveData, write it in getCyberdeckSaveData, validate its shape and assign it in loadCyberdeckSaveData.

offlineEntity recursion can crash at grid corners when the target lands on the player
src/CyberDeck/models/netrunningMinigame.ts:234-244

When the entity being marked offline is at the player's location, the function recurses with NetrunningState.grid[y + 1][x + 1]. If the player is at the bottom-right corner (or the last row), grid[y + 1] is undefined and undefined[x + 1] throws. The corrupted netrun spawns offline nodes in the corners, so this is a real path once spreading brings a node to the player.

Guard both indices: const next = NetrunningState.grid[y + 1]?.[x + 1]; if (next) offlineEntity(next); — or pick a safe adjacent tile that isn't the player and isn't out of bounds.

API gaps

★ No server.canUpgradeRam() — cost getter still returns Infinity when maxed
src/CyberDeck/cyberdeckApi.ts:397 (server.getRamUpgradeCost)

When RAM is maxed at 28, getCyberdeckServerRamUpgradeCost returns componentCost fields = Infinity. The API spreads that into {rom: Infinity, ..., money: Infinity}. Scripter code like if (cost.money < player.money) upgrade() reads "money we need is Infinity, so we can't afford it" — no way to distinguish that from "expensive but not maxed".

Still no API to observe netrun trace cooldown / decay progress — getNetrunningTraceFraction exists internally
src/CyberDeck/cyberdeckApi.ts (Cyberdeck namespace); src/CyberDeck/models/netrunRewards.ts:43

Scripters have netrun.getNetrunningCost(), but no way to tell if that number is a peak (just netran) or approaching the floor (safe to run again). getNetrunningTraceFraction exists in the model but isn't exposed. To time optimal netruns they'd have to poll cost repeatedly.

Expose netrun.getTraceFraction(): number (and a corrupted variant if you keep the parameter), or netrun.getMsSinceLastRun(): number. Give the number a stable, documented meaning.

Footguns for scripters

Fractional modStorageSize from skill chips is still silently wasted
src/CyberDeck/models/moduleMutation.ts:290; comparisons in netrunRewards.ts:57, cyberdeckApi.ts:240, NetrunningPortal.tsx:95

Skill chips add fractional slot counts (e.g., +0.32), so modStorageSize becomes 8.32. The gate is modStorageSize >= storedModules.length: 8.32 >= 9 is false, so the 9th slot never materializes. The player pays for a bonus that never becomes an actual slot. UI displays Math.floor(modStorageSize) = 8, so the fractional part is invisible to the player entirely.

Ceil-on-consumption: CyberdeckState.modStorageSize += Math.ceil(stats.mod_storage), or floor at compare time and reserve worst-case reward slots (see storage-overflow bug).

getID can still pick a 32-value ID space
src/CyberDeck/utils/statRng.ts:256

baseOptions = [2, 8, 12, 16]; for base 2, IDs are Math.floor(random * 32).toString(2) — 32 values. A player with many stored mods can hit collisions frequently; the retry loop only re-rolls the numeric portion, so if the RNG keeps landing on base 2 and all 32 are taken, it spins forever.

Drop base 2 or bump the exponent: const baseOptions = [8, 12, 16]; gives at least 32,768 IDs per base.

Cores upgrade still has no cap — player can grind cpuCores to arbitrary values
src/CyberDeck/models/cyberdeckServer.ts:91-127

There's still no canUpgradeCyberdeckServerCores. Player can push cpuCores past what grow/weaken formulas were tuned for. The UI now surfaces a "Cannot afford" toast (nice), but there's no "Maxed" state.

Either add a cap parallel to RAM's 28 and expose canUpgradeCyberdeckServerCores, or document uncapped and telegraph diminishing returns in the cost curve.

installMod still costs 1 second each — batch installs are slow
src/CyberDeck/cyberdeckApi.ts:120

Every installMod awaits helpers.netscriptDelay(ctx, 1000). A loadout swap of 5 mods takes ~5s of wall time. Doesn't scale for auto-swapping.

Either shorten the delay (200-500ms), or add an installMods(ids: string[]) batch method with a single delay, or document the delay in the JSDoc.

favoriteMod on the IO Panel silently mutates a throwaway copy
src/CyberDeck/cyberdeckApi.ts:98-106 → getModOrThrow:46-61; createModule.ts:32 (getCyberdeckIOPanel)

getCyberdeckIOPanel() returns a fresh object literal every call. The API now allows favoriting the IO panel (fixes prior "swallows error" issue) — but the mutation happens on the returned copy, which is GC'd. Nothing is persisted. Scripter sees the log line "Mod ... is now favorited" and thinks it worked.

Either persist the IO panel state (store ioPanelFavorite on CyberdeckState and read from it in getCyberdeckIOPanel), or reject favoriting with an explicit message ("The IO Panel cannot be favorited").
