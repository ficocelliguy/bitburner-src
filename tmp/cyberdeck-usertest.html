Wrote a small script pack (netrun loop, icebreaker crafting, storage manager with a mod-scoring heuristic, auto-installer, cortex-share, a greedy wiring solver, orchestrator). Eight Jest tests pass, including a 10-second live end-to-end and a wire-from-scratch test where the solver rebuilt the starter kit's wiring exactly. Two headlines: the MVP API is enough to build a working auto-farm including a basic wiring solver, but a scripter has no way to see trace-decay progress, so netrun cadence is guesswork — early-game decks sit idle most of the time.

Scripts I wrote

cyberdeck/main.js — orchestrator
tmp/cyberdeck-scripts/cyberdeck/main.js

Kicks off the five child scripts if the player has a deck. ns.run(path, threads) in a loop; skips duplicates via ns.isRunning.

cyberdeck/netrun.js — main farming loop
tmp/cyberdeck-scripts/cyberdeck/netrun.js

Netruns whenever getNetrunningCost() is at or below a cheap-cadence cap (default 3 icebreakers) and there's storage headroom for the ~3 mods a netrun returns. Otherwise it prints why it's waiting.

cyberdeck/craft-icebreakers.js — keeps a stockpile
tmp/cyberdeck-scripts/cyberdeck/craft-icebreakers.js

Targets 8 icebreakers on hand. Reads the crafting cost once, computes what it can afford this tick from the shared component pool, batches it into a single craftICEBreaker(count) call.

cyberdeck/manage-storage.js — recycle trash, favorite gold
tmp/cyberdeck-scripts/cyberdeck/manage-storage.js

Hand-rolled scorer in cyberdeck/score.js weights component-production, hacking, and faction-rep mults. Auto-favorites anything above 25 so it won't get recycled by accident; recycles the worst non-favorited mods to keep at least 5 free slots.

cyberdeck/auto-install.js — swap in upgrades, feed skill chips, re-wire
tmp/cyberdeck-scripts/cyberdeck/auto-install.js

Three jobs. (1) Install any stored SkillChip so charging it hands out a permanent buff. (2) If a stored mod scores at least 5 points above a same-type rack mod, store the old one and install the new one in its slot. (3) After any change, call wireUpAll(ns) from wire.js so the newly-installed mod actually gets charged.

cyberdeck/wire.js — greedy wiring solver
tmp/cyberdeck-scripts/cyberdeck/wire.js

BFS from the IO panel. For each uncharged mod, walks the charged set looking for any shared socket index where both ends are free, then addConnections them. Any pair+socket that fails (overlap) gets blocked so we don't retry it forever. Rewires the starter kit exactly (IO→PSU on 3, PSU→proc on 0, PSU→uplink on 6) from a blank connection state in the test. Doesn't re-order mods on the rack to route around overlaps — that's the honest limit of a script that can only see socket colors, not the physical wire layout.

cyberdeck/cortex-share.js — neurode farm
tmp/cyberdeck-scripts/cyberdeck/cortex-share.js

Trivial: while (true) await ns.cyberdeck.cortexShare();. Run with as many threads as spare RAM allows.

cyberdeck/score.js — the scoring heuristic every other script needs
tmp/cyberdeck-scripts/cyberdeck/score.js

Weights player-mult buffs (hacking, faction_rep, hacking_speed, hacking_money…) and other-mult buffs (romProduction, chipProduction, neurodeProduction) to match the "component production, hacking, faction rep" goals. Skill chips and rack extensions get a flat bonus so they beat vanilla mods. Exists only because there's no built-in comparator.

What worked well

The typed return shapes are clean

getComponentCounts(), getStoredMods(), getInstalledMods(), getNetrunningCost() all return exactly what you want; no wrapper objects, no success/error envelopes. The netrun gate ended up three lines that read like the docs example.

getInstalledMods() returns a charged flag

Without it a script has to walk the connection graph to know which mods are contributing stats. With it: ns.cyberdeck.getInstalledMods().filter((m) => m.charged).

craftICEBreaker(count) takes a batch count

Crafting loop didn't have to spin one call per icebreaker; fits the "top up to target" pattern cleanly. The mod crafters can't do this because each returns the specific rolled mod, which is fair.

getRackCapacity() exists and includes rack-extension bonuses

Auto-installer needs to know when the rack is full before trying to install a skill chip. getRackCapacity() includes charged rack-extension slots, not just the base 5, which is what a scripter actually wants.

recycleMod returns the components refunded

Storage script can log "recycled X, +2 ROM +2 chips" without a second call to diff the pool.

favoriteMod() composes cleanly with a scoring pass

"Favorite above threshold; recycle worst first" is a two-line pattern. Same call as the right-click UI, so scripted and hand-managed decks don't drift apart.

addConnection is a safe probe (no side effects on failure)
src/CyberDeck/models/moduleMutation.ts:126-135

The wire-overlap check happens before the two disconnectSocket calls, so a failed addConnection leaves state untouched. That's the property that makes scripted wiring viable — wire.js can enumerate every candidate triple and try each one without worrying about clobbering existing wires. Nothing in the docs advertises this; it's worth calling out as a stable contract.

Basic wiring is scriptable end-to-end

Given getInstalledMods() (with the charged flag), getConnections(), getCyberdeckIOPanel().sockets, and a safe-to-probe addConnection, a scripter has everything needed for the "charge every uncharged mod" case. wire.js is ~55 lines and it works. I originally listed this as an API gap; the gap is narrower than I thought.

Confusing or hard to use

Cost is the only proxy for trace decay, and it's the wrong shape

The policy I want to write is "netrun when trace decay is under 50%." The only signal is getNetrunningCost(), which spikes to hundreds right after a run and creeps back down. I had to pick a magic max-cost threshold (I chose 3) and hope. In the 10s run the cost went 1 → 441 → 163 → 39, never getting back under 3, so the loop stayed idle after the first run.

Expose ns.cyberdeck.getNetrunningTraceFraction() (already on src/CyberDeck/TODO.md). Then policy can be phrased the way the player thinks about it: "netrun when trace is under 20%" or "burn ICE hard, netrun continuously."

Mod type strings aren't in ns.enums
src/ScriptEditor/NetscriptDefinitions.d.ts:10390 (NSEnums)

mod.type is typed ModType on the returned DeckMod, but the enum isn't on ns.enums. A scripter hardcodes "SkillChip", "Rack Extension", etc. as string literals, with no autocomplete. And the strings are inconsistent — see footgun below.

Add ModType: ModTypeEnumType to NSEnums, same treatment as CrimeType, JobField, etc.

ComponentCounts key casing is a mixed bag
src/ScriptEditor/NetscriptDefinitions.d.ts:4397 (ComponentCounts)

ROM (all caps), ICEBreakers (PascalCase-ish), chips / neurodes / cores (lowercase). Every script that touches the pool has to remember which is which. Tripped on this while writing util.canAffordCost().

Pick one. All-lowercase (rom, iceBreakers) matches the rest of the NS API. If renaming's too disruptive, at least call it out at the top of the docs page's "Crafting Components" section.

A stored mod is an opaque bag of buff/debuff numbers; no notion of "score"

Had to invent score.js to answer "should I install this or recycle it?" Fine that the scoring choice is gameplay, but a scripter has no baseline to lean on. Even a raw-magnitude helper would let people filter dumpster-fire mods. Right now every scripter reimplements the same rough heuristic.

Optional: ns.cyberdeck.stats.evaluateMod(mod) returning something like { buffMagnitude, debuffMagnitude, rarityBias }. Doesn't need to be smart, just consistent across scripters.

Bare boolean return from installMod hides why it failed
src/CyberDeck/cyberdeckApi.ts:98-111

The impl distinguishes "mod not found" (throws) from "rack full" (returns false + log line). A script just sees false — could be rack full, invalid index, or something new added later. Only signal is the log.

Either throw for rack-full too (so the caller can catch specifically), or return { success, reason }. Matches netrun's { success, mods, components } shape.

Mod IDs like 0z5B423 don't correlate to anything the UI shows

Cute flavor (base-2/8/12/16 prefixes), but when the storage manager logs Recycled [r0 Uplink 0b110] there's no way to correlate that back to the rack UI without visually hunting.

Not a bug, footnote. A helper like ns.cyberdeck.describeMod(mod) that returns the same string the UI shows would make script logs a lot friendlier.

API gaps

getNetrunningTraceFraction — single most useful missing method
src/CyberDeck/TODO.md (already on the list)

Scripters guess "how long since my last run" via icebreaker cost. That's a proxy that also depends on netrunningCooldownLevel, which changes over time. Any rate-policy script has to reverse-engineer the cost formula.

Expose the function that already exists internally (getNetrunningTraceFraction).

Wire-overlap state isn't queryable from a script

Scripted wiring works for the easy case (see the "Basic wiring is scriptable" win), but the greedy solver in wire.js can only learn about a wire-overlap by trying a connection and having it fail. For a mod that shares three sockets with the IO panel but two of them are covered by wires between other mods, the solver has to probe until it stumbles onto the working one. On a big rack this scales poorly. CyberdeckState.coveredSockets exists internally — nothing on the NS surface exposes it.

ns.cyberdeck.getCoveredSockets(): Socket[] — same shape as getConnections()'s Socket. Then a solver can skip covered sockets up front instead of finding out the hard way.

IO-panel socket layout isn't documented anywhere script-visible
src/CyberDeck/models/createModule.ts:37 (IO panel sockets = [f,t,f,t,f,t,f,f])

The panel has sockets on indices 1, 3, 5 only. If your first-installed mod only has sockets on 0, 2, or 4 — RNG rolls this — the IO panel can never charge it directly. A script can discover it via getCyberdeckIOPanel().sockets, but only if the scripter knows to look. Docs page doesn't mention it.

One sentence in the docs page's "Wiring Up Mods" section: "The deck IO panel only has sockets on the indices marked in getCyberdeckIOPanel().sockets — currently 1, 3, and 5."

No unified "list all craft costs"; four separate getXCraftingCost() calls
src/CyberDeck/cyberdeckApi.ts:300-303

Nit. A "what should I craft next?" script needs all four costs — four calls, four names, no mod type in the return value.

ns.cyberdeck.crafting.getAllCraftingCosts() → Record<ModType, ComponentCounts>. Keep the individual getters for compatibility.

modStorageSize is buried inside stats.getLevels()
src/CyberDeck/cyberdeckApi.ts:216-225

"Is storage nearly full?" requires ns.cyberdeck.stats.getLevels().modStorageSize — awkward path for a capacity value that isn't really a "level." Bumped into it twice while writing netrun.js.

Mirror getRackCapacity(): add top-level ns.cyberdeck.getModStorageCapacity(). Keep getLevels() as-is.

No way to preview "will this mod be wire-able if I install it here?"

A scripted upgrade swap can install a strictly-better mod that ends up dead because none of its sockets overlap the neighbors it landed next to. wire.js can retry after the fact, but it can't answer the question before the swap — so auto-install occasionally throws away a good rack mod for a stored mod that never charges. Would be much nicer to check first.

ns.cyberdeck.previewInstall(modId, index): { chargeable: boolean, possibleConnections: Connection[] }. Would let auto-install rank swap candidates not just by score but by whether they'll actually get charged.

Footguns

"SkillChip" has no space; "Power Supply", "Processing Mod", "Rack Extension" do
src/ScriptEditor/NetscriptDefinitions.d.ts:4464-4471 (ModType enum)

A newer coder will guess mod.type === "Skill Chip" — matching every other multi-word mod type — and their skill-chip auto-installer will silently never run. Got this wrong first try; only caught it because the test asserted "at least one skill chip installed."

Rename the enum value to "Skill Chip" so it matches its siblings. Nothing else in ModType uses PascalCase.

installMod and netrun both return promises; only one is loud about it

Docs example for installMod uses await; the type is Promise<boolean>. Forget the await and there's no runtime error — the next call runs against pre-install state. auto-install.js initially had a race where a bare installMod and an immediately following storeMod fought each other.

One-line doc note at the top of the API: "All deck-mutating methods (installMod, storeMod, netrun, cortexShare, upgrades) must be awaited." Or make storeMod return a promise too so the pattern is uniform.

ns.cyberdeck.legacy.getCost() returns Infinity pre-glitch; easy to divide by
src/CyberDeck/cyberdeckApi.ts:437-443

Pre-glitch, legacy.getCost returns Infinity and prints a corrupted hint. A script that treats getCost as a number happily does if (cost < myBudget) — always false, so silent — but any arithmetic (percent of budget, ratio to non-legacy cost) yields NaN and poisons everything downstream.

Either return NaN (at least loud in comparisons) or throw "glitch not yet discovered" so scripters know to gate on their own discovery signal.

Storage overflow on netrun silently corrupts inventory
src/CyberDeck/cyberdeckApi.ts:177-181 (see also related bug in the code review)

Netrun API guard is modStorageSize < storedModules.length. At exactly full (8/8) the guard passes and 3 new mods get unshifted → 11/8. netrun.js defends with STORAGE_HEADROOM = 4, but only because I read the source. A scripter following the docs example will overflow.

Cross-references the "Netrun succeeds with 0 free storage slots" bug in the code review; fixing it there fixes the script-facing footgun too.

cortexShare has no documented thread ceiling but diminishes fast
src/ScriptEditor/NetscriptDefinitions.d.ts:4674-4687

Docs say "diminishing returns" with no shape. A player will run ns.run("cortex-share.js", -1) (all RAM) — fine for a 4GB deck (1 thread), thousands wasted on a big pserver. My script hardcoded 16 and I have no idea if that's high, low, or right.

Either a doc line ("returns follow 10*n/(n+300)-ish, sweet spot is ~30 threads") or a ns.cyberdeck.getCortexShareRate(threads) helper so scripters can plot the curve themselves.

wire.js on a blank connection state — rebuilds the starter kit exactly

Cleared every starter connection so all 3 mods were dead, then ran cyberdeck/wire.js. 

  wired 0o46317 <-> cyberdeck-io-panel on socket 3    (power supply)
  wired 0xC4E43 <-> 0o46317 on socket 0                (processing mod)
  wired 0z9119  <-> 0o46317 on socket 6                (uplink)
charged 0->3 (attempted=3, connected=3)

Solver picked the only viable path: IO panel has sockets 1/3/5, PSU has 0/3/6 — one shared color (3), so wire that first. Then PSU becomes the source for the other two mods on their unique sockets (0 and 6). Same wiring the starter kit ships with. No overlap failures on this rack.
